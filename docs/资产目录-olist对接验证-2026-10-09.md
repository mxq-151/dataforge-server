# 资产管理模块 × 容器内 olist 数仓 —— 对接验证报告

- 验证时间：2026-10-09 21:40 (GMT+8)
- 被测对象：容器 `dataforge-allinone`（dataforge-server `:8082`、DolphinScheduler `:12345`、PostgreSQL `:5432`）
- 验证方式：直连数仓/元数据库核对 + 实调 `/api/asset/*` 全部只读接口 + 对照后端源码与运行日志
- 结论一句话：**模块骨架与权限链路是通的，但"存储侧"三个关键事实（分区表大小、行数、日度快照）和"调度侧"整个接入都没接上；其中 5 项是代码/配置缺陷，不是数据没准备好。**

## 二、数据版图（先对齐"真实"）

数仓全部落在容器内 PostgreSQL 的 **`test_db`** 库（属主 `test_tenant`），共 **7 个 schema / 75 张表**：

| schema | 表数 | 说明 | 真实占用 |
|---|---|---|---|
| `test_db`（public） | 9 | `olist_*_dataset` 原始源表 | 204 MB |
| `ods_olist_test` | 18 | 9 张父表 + 9 张 `_default` 分区 | 325 MB |
| `dwd_olist_test` | 6 | 3 + 3 | 175 MB |
| `dws_olist_test` | 18 | 9 + 9 | 48 MB |
| `dim_olist_test` | 6 | 普通表 | 38 MB |
| `ads_olist_test` | 17 | 8 + 8 + 1 普通表 | 144 KB |
| `dqc_olist_test` | 2 | 规则表 + 结果表 | 96 KB |

三个必须知道的结构事实：

1. **分区只有 `_default` 一个**：`ods_olist_orders_d` 这类父表是 PG 声明式分区表（`relkind='p'`），
   但 `pg_inherits` 里只挂了 `xxx_d_default`，没有任何按 `dt` 的真实分区 —— 所有行都躺在 `_default` 子表里。
   因此 **父表 `pg_total_relation_size()` 恒为 0**，真实体积只在子表上。
2. **`dt` 不是装载日期而是业务日期**：`ods_olist_orders_d` 的 `dt` 从 2016-09-04 一直到 2018-09-03（634 个取值），
   所以即便将来按 `dt` 建真分区，也起不到"按天增量"的作用。
3. **调度侧实际情况**：DS 里 6 个工作流（ods/dim/dwd/dws/ads/dqc）全部已上线，
   `t_ds_schedules` **0 行（无任何 cron）**；`t_ds_workflow_instance` 52 行 —— ods/dim/dwd 各 17 次成功、
   dws 1 次仍在运行、**ads 与 dqc 从未执行过**（所以 `ads_olist_*` 9 张表全空）。

元数据侧（dataforge 库）只有 **1 个数据源**：`test_datasource` → `jdbc:postgresql://127.0.0.1:5432/test_db?currentSchema=test_db`。

## 三、问题清单（按优先级，附证据）

### P0-1 调度系统压根没接（影响 3 个看板 + 1 个页签）

容器内生效配置（解包 jar 内 `BOOT-INF/classes/application.yml`）：

```yaml
scheduler:
  dolphinscheduler:
    base-url: ''      # ← 空
    token: ''
    default-project-code: '1'
```

后端日志直接印证：

```
2026-10-09T06:58:51  SchedulerTaskMetricsCollectTask : 调度任务指标采集跳过：日期=2026-10-08, 原因=调度系统未配置
```

连带结果：`/asset/table/{id}/producers` 恒返回 `[]`；`/asset/inventory/task-delay` 恒 `totalTasks=0`；
`/asset/inventory/top-compute` 恒 `[]`；`scheduler_task_run_daily` 永远 0 行。
而真实侧有 52 个流程实例、603 个任务实例可供统计 —— 全是"该有的没有"。

> 附带确认：`SchedulerApiClient` 打的 `/projects/{code}/process-instances` 与 DS 3.4.1 的
> `/workflow-instances` 实测都返回 200，所以**配好 base-url + token 就能直接生效**，不必改路径。

### P0-2 分区父表大小恒为 NULL → 存储体积全线失真（最严重的数据错误）

链路：

1. `AbstractJdbcExecutionStrategy.removePostgresPartitionChildren()` 有意剔除 `relispartition=true` 的子表
   （注释说明是为了避免"同一逻辑表出现两份、分区壳表没注释"）——**这个取舍本身合理**；
2. 但 `JdbcTableStatsCollector` 的 PG 取数 SQL 是
   `SELECT c.relname, pg_total_relation_size(c.oid) ... WHERE c.relkind IN ('r','p','m','f')`；
3. PG 语义下分区父表 `pg_total_relation_size` = **0**，而 `TableStorageSizeRefreshService` 又 `if (size <= 0) continue;`
   → **20 张分区父表的 size_bytes 永远是 NULL**；子表的真实体积因为不在 `table_metadata` 里而直接被丢弃。

实测对照：

| 表 | 模块 size_bytes | 数据库真实值 | 偏差 |
|---|---|---|---|
| `ods_olist_test.ods_olist_orders_d` | `null` | 24,428,544 B（在 `_default` 子表） | 全丢 |
| `dws_olist_test.dws_olist_category_d` | `null` | 2,973,696 B（在 `_default` 子表） | 全丢 |
| `dim_olist_test.dim_olist_customers_d` | 8,192 B | 21,037,056 B | **约 1/2568** |
| `dqc_olist_test.dqc_olist_rule_d` | 32,768 B | 32,768 B | ✅ 一致 |

模块报出的 `totalSizeBytes = 179,683,328`（171 MB），**其中 179,568,640 B（99.93%）全在「未分类」的 9 张源表上**，
六个数仓分层合计只有 **114,688 B（112 KB）**，而真实总数是 **631 MB**。

`/asset/inventory/overview` 实测返回：

```json
"byLayer": [
  {"layerCode":"dws","tableCount":9,"sizeBytes":8192},
  {"layerCode":"ods","tableCount":9,"sizeBytes":0},      // ← 真实 325 MB
  {"layerCode":"ads","tableCount":9,"sizeBytes":8192},
  {"layerCode":"__unclassified","tableCount":9,"sizeBytes":179568640},  // ← 源表被塞进"未分类"
  {"layerCode":"dim","tableCount":6,"sizeBytes":65536},
  {"layerCode":"dwd","tableCount":3,"sizeBytes":0},      // ← 真实 175 MB
  {"layerCode":"dqc","tableCount":2,"sizeBytes":32768}
]
```

连带 `/asset/inventory/size-growth`（数据大小增长率）永远为空 —— 它既依赖日快照，也依赖可比的 size。

### P0-3 `row_count` 没有任何写入路径（47/47 全空）

- `MetadataSyncService:223` 只做 `target.setRowCount(source.getRowCount())`，而 `source` 来自
  `listTables()`，该方法**只填**大小/时间/分区列/压缩，从不填行数；
- `TableStorageSizeRefreshService` 只 `set(TableMetadata::getSizeBytes, size)`，不碰行数；
- 全仓搜索 `setRowCount`，其余命中都在读侧（VO 拷贝）。

实测：`/asset/table/65`（`ods_olist_test.ods_olist_geolocation_d`）返回 `"rowCount": null`，
真实行数 **1,000,163**；`dwd_olist_order_item_detail_d` 真实 112,650 行、`dws_olist_category_d` 19,035 行，同样为空。

### P0-4 三张日度汇总表全空（增长率 / 热度趋势 / 延迟率 全部无源）

| 表 | 行数 | 产出任务 |
|---|---|---|
| `asset_catalog_daily` | 0 | 资产目录快照（每日 02:30） |
| `asset_usage_daily` | 0 | 热度汇总（每日 01:30） |
| `scheduler_task_run_daily` | 0 | 调度指标采集（每日 03:30） |

日志证据：

```
2026-10-09T02:15:00  TableStorageSizeRefreshTask  : 表存储大小刷新任务完成：数据源=1, 更新表数=0, 失败数据源=0
2026-10-09T02:29:59  AssetCatalogSnapshotService   : 资产目录快照：2026-10-08 无纳管资产
2026-10-09T02:29:59  AssetCatalogSnapshotTask      : 资产目录快照任务完成：日期=2026-10-08, 资产数=0, 清理=0
2026-10-09T06:44:23  MetadataSyncService           : 全量同步完成: datasourceId=1, 成功=47, 失败=0
```

即：**元数据是在 06:44 才同步进来的，而 02:15/02:30 的定时任务跑在它之前**，统计到 0 张表。
`scheduler_task_run_daily` 则叠加了 P0-1（DS 未配置）。

结果：`/asset/inventory/size-growth` = `[]`；`/asset/table/65/usage` 30 天全 0；
`/asset/inventory/task-delay` = 全 0。

### P1-5 记录下来的 size_bytes 全是"空表时代"的旧值

`TableStorageSizeRefreshService` 最后一次成功执行是 02:15（在 06:44 数据装载之前），之后没有重跑过。
于是 19 张非分区表的值都停留在建表后不久的状态，例如：

| 表 | 模块值 | 当前真实值 |
|---|---|---|
| `dim_olist_test.dim_olist_customers_d` | 8,192 B | 21,037,056 B |
| `dim_olist_test.dim_olist_products_d` | 16,384 B | 7,135,232 B |
| `dim_olist_test.dim_olist_date_d` | 8,192 B | 131,072 B |

（`dqc_olist_rule_d` 恰好一致，是因为它本来就小、没怎么变。）

### P1-6 源表被解析出「伪业务域」与「无环境」，污染两个看板的聚合口径

`TableNameConventionParser` 对 `olist_customers_dataset` 这类源表：
首段 `olist` 不是分层 → `layerCode=null`（进「未分类」，合理）；
但第 2 段 `customers` 满足业务域正则 → **`domainCode="customers"`**（不合理）。

后果（`/asset/inventory/overview` 实测）：

```json
"byDomain": [
  {"domainCode":"olist","tableCount":38,"sizeBytes":114688},
  {"domainCode":"order","tableCount":3,"sizeBytes":70066176},
  {"domainCode":"customers","tableCount":1,"sizeBytes":11919360},
  {"domainCode":"geolocation","tableCount":1,"sizeBytes":70885376},
  {"domainCode":"orders","tableCount":1,"sizeBytes":22749184},
  {"domainCode":"products","tableCount":1,"sizeBytes":3620864},
  {"domainCode":"sellers","tableCount":1,"sizeBytes":311296},
  {"domainCode":"category","tableCount":1,"sizeBytes":16384}
]
```

`order/customers/geolocation/orders/products/sellers/category` 这 7 个"业务域"全部是解析伪影，
真实业务域只有一个 `olist`。

同时 `AssetEnvParser` 按库名末段识别环境，`ods_olist_test` → `test`（OK），
但源表所在库名 `test_db` 末段是 `db` → 返回 `null` → **204 MB 的源表被排除在环境维度之外**：

```json
"env-project": [{"env":"test","projectCode":"test_project","projectName":"测试项目","tableCount":38,"sizeBytes":114688}]
```

即"环境 × 项目"看板只剩 38 张（几乎没数据的）分层表、112 KB，把真正占 204 MB 的源表整层漏掉。

### P1-7 dqc 层 29 条质检规则完全没有被资产模块识别

数仓里客观存在：

```
test_db.dqc_olist_test.dqc_olist_rule_d    → 29 行，target_object 形如
   ods_olist_test.ods_olist_order_reviews_d.review_score
   ods_olist_test.ods_olist_order_items_d.price
dqc_olist_test.dqc_olist_result_d          → 29 行
```

但模块的质检信息读的是 dataforge 库自己的 `dq_task` / `dq_task_rule_rel`，两者**都是 0 行**。实测：

- `/asset/table/65/quality` → `{"ruleCount":0,"enabledRuleCount":0,...}`
- `/asset/inventory/health` → `NO_QUALITY_RULE = 47`（把全部 47 张表都判成"无质检规则"）

这是把"数仓侧已有质检资产"和"平台侧质检任务"两套东西混为一谈造成的漏报。

### P2-8 存储位置 / 存储格式 / 最后修改时间恒为空

`AssetTableDetailVO.location / storageFormat / lastModifyTime` 在 PG 数据源上拿不到：
PG 没有 HDFS 路径与文件格式概念，`JdbcTableStatsCollector.queryPostgres()` 也没有填 `lastModifyTime`
（PG 无 `information_schema.TABLES.UPDATE_TIME`）。前端目前展示为空串，
建议按引擎提示"不适用"，而不是留空让人以为同步失败。

### P2-9 数仓自身还有一半没跑完（会影响验收印象）

- `ads_olist_test` 9 张表 **全部 0 行**，且 DS 里 `olist_code_ads_prod` **从未执行过**（0 个实例）；
- `dqc` 工作流同样 0 个实例（但规则/结果表有 29 行，应是直接 SQL 写入）；
- `dws` 里 `region / repurchase / review / seller` 4 张表 0 行，且此刻 dws 工作流仍是 RUNNING。

这部分不是资产模块的锅，但会让人误判"资产模块没数"。建议验收前先把 ads 层跑通。

### P2-10 非超管账号看不到数据预览（待确认）

用租户 `test_tenant` 下、角色 `DATA_DEV_ENGINEER` 的等价 token 调
`/asset/table/65/preview`：

```json
{"code":500,"message":"预览失败：系统异常: 权限不足：无权对表 \"ods_olist_test\".\"ods_olist_geolocation_d\" 执行 SELECT 操作"}
```

堆栈指向 `AbstractBaseExecutionStrategy.checkDmlTablePermission`。
但 `sys_table_permission` 已有一条 `test_datasource / ods_olist_test / table_names='*' / can_select=1`，
且通过 `sys_role_table_permission` 授给了该租户的角色，**目录树对同一账号是可见的**
（说明权限解析链路本身认得这条授权）。超管账号调用同一接口正常返回数据。

→ 目录树与本 DML 校验的口径不一致，怀疑是缺陷，但需要用一个"真实登录的非超管账号"再复现一次才能定性。

## 四、修复建议（按投入产出排序）

| 优先级 | 动作 | 位置 |
|---|---|---|
| P0 | 给容器注入 DS 接入配置：`scheduler.dolphinscheduler.base-url=http://127.0.0.1:12345/dolphinscheduler`、`token=<t_ds_access_token.token>`、`default-project-code=183115978154240`。配完 producers / 延迟率 / TOP 算力即刻有数 | 启动参数或 `application.yml` |
| P0 | PG 取大小改为**父表聚合子表**：`SELECT c.relname, pg_total_relation_size(c.oid) FROM ...` 换成按 `pg_inherits` 递归汇总，或在 `removePostgresPartitionChildren` 时把子表体积累加到父表。这是 631 MB → 171 MB 失真的根因 | `JdbcTableStatsCollector.POSTGRES_STATS_SQL` |
| P0 | 补 `row_count` 写入路径：PG 用 `pg_stat_user_tables.n_live_tup`（或 `reltuples`）随 size 一起刷新；行数刷新并入 02:15 任务 | `JdbcTableStatsCollector` + `TableStorageSizeRefreshService` |
| P1 | 把三个日度任务改成"依赖元数据就绪"：任务开销时若 `table_metadata` 为空/同步时间早于任务时间，则跳过并 WARN，或直接在元数据同步成功后**顺带触发一次**快照/热度汇总 | `AssetCatalogSnapshotTask` 等 |
| P1 | 源表解析收敛：库名不是标准 `{分层}_{业务域}_{环境}` 时（如 `test_db`），
       业务域不应从表名第 2 段猜；建议 `layerCode` 为空时 `domainCode` 一律置空，
       并把源表统一归入一个显式的"贴源/外部"层，避免污染 `byDomain` | `TableNameConventionParser` |
| P1 | 环境识别补一条兜底：库名不含 `_prod/_gray/_test` 时，若其下全是未分类源表，可归入 `unknown` 分组并**计入总量**，而不是整层丢弃 | `AssetEnvParser` + `AssetInventoryService.envProject` |
| P1 | 质检对接：`quality()` 除 `dq_task` 外增加对 `{层}.dqc_*_rule_d` 的读取（或做一次数仓规则→平台任务的映射），否则"质检覆盖"这个指标永远是 0 | `AssetCatalogService.quality` |
| P2 | 明细页按引擎屏蔽 `location/storageFormat`，并给 `lastModifyTime` 提供 PG 的替代口径（如 `pg_stat_user_tables.last_autovacuum` 或 `pg_class.relfilenode` 变更时间） | `AssetCatalogService.detail` |
| P2 | 复核非超管预览的权限口径与目录树是否一致 | `AbstractBaseExecutionStrategy.checkData` |

## 五、复现命令（可原样粘贴）

```bash

select n.nspname, c.relname, c.relkind, c.relispartition, pg_total_relation_size(c.oid)
from pg_class c join pg_namespace n on n.oid=c.relnamespace
where (n.nspname like '%olist%' or n.nspname='test_db') and c.relkind in ('r','p') order by 1,2\""

docker exec -e PGPASSWORD=<pg_pwd> dataforge-allinone bash -lc \

# 5) 接口（需带租户的 Token）
```

## 六、一句话总结

资产目录模块的**接口、权限、目录树、检索、治理项统计都是好的**；
坏在两条链路上：**① DS 接入没配（3 个看板全空）**，**② 分区表的"父表 0 字节 + 行数无采集"（体积少算 3.7 倍、行数全空、增长率/环境看板失真）**，

### 待决策：P1-7 数仓 dqc 规则要不要接

现象：数仓 `dqc_olist_test` 有 29 条规则 + 29 条结果（`target_object` 形如
`ods_olist_test.ods_olist_order_reviews_d.review_score`），但资产模块的质量摘要只读平台自己的
`dq_rule`（0 行），于是质检页恒 0、`NO_QUALITY_RULE = 47`。

两条路，需要你定：

- **A. 把规则注册进平台 DQ 模块**（推荐）：平台本就有完整的 `dq_rule`/`dq_rule_result` 与 DQ 页面，
  这样资产页与 DQ 页看到的是同一套规则，不会出现"两个规则源"。
  代价：需要一次数据/接口导入（不是资产模块的代码改动）。
- **B. 资产模块增加数仓 dqc 表的只读兜底**：资产页立刻正确，但会在平台 DQ 模块之外引入第二个规则源，
  两个页面可能显示不一致，且给资产详情加了一条 JDBC 查询路径。
