# 表访问频率采集链路 + 资产管理表设计评估

- 评估时间：2026-10-10 (GMT+8)
- 被测仓库：`dataforge-server`（后端）+ `dataforge`（前端）
- 方法：通读 `modules/asset` 全量源码 + 前端 `assetCatalog.ts` / `AssetCatalogPanel.tsx` / `AssetDetailTabs.tsx`
  + 4 方言 `sql/init/*.sql` 逐表比对

---

## 一、访问频率现在是怎么采的

### 1.1 唯一入口是前端埋点，且只在资产目录面板

```
AssetCatalogPanel.tsx  track()
   └─ POST /api/asset/access   (assetCatalogApi.reportAccess，suppressError=true 静默降级)
        └─ AssetUsageService.recordAccess(dto)
```

`track()` 的全部触发点（前端全仓库仅此 4 处，已 grep 确认）：

| 触发动作 | assetType | accessType | 代码位置 |
|---|---|---|---|
| 目录树点选表 | `table` | `browse` | AssetCatalogPanel.tsx:849 |
| 搜索结果打开表 | `table` | `browse` | AssetCatalogPanel.tsx:869 |
| 点击收藏 | `table` | `bookmark` | AssetCatalogPanel.tsx:886 |
| 详情页「数据预览」页签加载成功 | `table` | `read` | AssetDetailTabs.tsx:371 → onAccess('read') |

**关键事实：前端只上报 `assetType='table'`**。`column` / `indicator` / `query` / `keyword`
四个枚举值在 DTO 与后端校验里都存在，但**前端从不发送**。

### 1.2 后端写入：非关键路径、逐条 insert

`AssetUsageService.recordAccess()`：

- 白名单校验 `assetType ∈ {table,column,indicator}`、`accessType ∈ {browse,read,bookmark,query}`，
  非法项 **静默丢弃**（只打 debug 日志，不抛错），单次最多 200 条；
- `table` 类型直接落 `table_metadata_id = assetId`；`column` 类型反查 `column_metadata` 得到所属表 id；
- **逐条 `insert`**（循环里单条插，无批量）；
- 顺带实时回写 `table_metadata.last_access_time`（见 2.9 的批量语义缺陷）。

### 1.3 T+1 汇总：`AssetUsageRollupTask`

每日 **01:30** 定时（`@Scheduled(cron = "0 30 1 * * ?")`），也可 `POST /asset/task/usage-rollup/run`
（`SUPER_ADMIN`）手动跑，默认统计日 = 昨天，两步：

1. `rollupDaily(昨天)`
   - 拉取当天全部 `asset_access_log` 明细 → **内存**按 `(asset_type, asset_id)` 聚合
     （`browse`→browse，`read`/`query`→read，`bookmark`→bookmark）；
   - 逐条 upsert 到 `asset_usage_daily`（无则 insert，有则 update，按日覆盖 ⇒ 幂等可重放）；
   - 若当天有 `asset_type='column'` 的命中，回写 `column_metadata.hot_score` 星级。
2. `refreshTableCounters()`
   - 从 `asset_usage_daily` 取近 30 日 `SUM(browse_count)` / `SUM(read_count)`；
   - 从 `asset_bookmark` 取每表收藏数；
   - 从 `asset_access_log` 取每表 `MAX(access_time)`；
   - 逐表 `UPDATE table_metadata` 回写 4 个热度冗余列。

### 1.4 启动补偿

`AssetDailyTaskCatchUpRunner`（`ApplicationReadyEvent`）：仅当
`asset_catalog_daily` / `asset_usage_daily` **完全为空**且元数据最近同步晚于统计日时，补跑昨天一次。
「某天漏跑」不兜底，交给下一轮覆盖写。

### 1.5 消费端

| 消费点 | 数据来源 |
|---|---|
| `GET /asset/table/{id}/usage` 趋势 | `asset_usage_daily`（近 N 日） |
| 同上 · 字段热度 | `column_metadata.hot_score` + `asset_usage_daily`（asset_type='column'） |
| 同上 · 高频读者 | `asset_access_log` **原始明细**（read/query，按窗口 group by user_name） |
| `GET /asset/inventory/top-assets`（访问频率榜） | `table_metadata.browse_cnt_30d + read_cnt_30d` |
| 表详情热度卡 | `table_metadata` 4 个冗余列 |
| 治理项 `NO_ACCESS_30D` | `table_metadata.last_access_time`（`IDLE_DAYS=30`） |

## 二、发现的问题

### P0（影响功能正确性）

**P0-1 采集口径 ≠ 业务语义：「表访问频率」实为「目录页点击频率」**
埋点只在资产目录面板触发。真正的数据使用行为（数据探索 SQL 执行 `CodeExecutionService`、
调度任务读写、下游消费）**完全不采集**——已 grep 确认 `CodeExecutionService` 不引用任何 asset 埋点。
且 `read` 只在预览页签 `status==='ok'` 时打一次，代表"打开过预览"，不代表"取数用过"。

**P0-2 字段热度链路是死的**
前端从不发 `assetType='column'` ⇒ `asset_usage_daily` 永远没有 `asset_type='column'` 行
⇒ `rollupDaily` 里 `columnHits` 恒空 ⇒ `refreshColumnHotScore` 从不执行 ⇒
`column_metadata.hot_score` 恒 0 ⇒ 详情页「字段热度」拿不到 `hotScore` 也拿不到 `hitCount`，
**永远渲染"暂无字段热度数据"**。设计与实现脱节。

**P0-3 明细表无保留期，但类注释宣称有**
`AssetCatalogSnapshotService.RETENTION_DAYS = 180`、`SchedulerTaskMetricsService.RETENTION_DAYS = 180`
都有 `purgeBefore()` 配套。而 `asset_access_log` 与 `asset_usage_daily` **没有任何清理逻辑**，
`AssetUsageService` 类注释却写"明细表可以放心地按保留期清理"——注释与实现矛盾。
埋点表只增不删，且下面 P0-4 的全表扫描依赖它。

**P0-4 索引缺口：`asset_access_log` 没有 `table_metadata_id` 索引**
现有索引仅 `(asset_type,asset_id)`、`(access_time)`、`(user_id)`（4 方言一致）。
但两个热点查询都打 `table_metadata_id`：

- `refreshTableCounters`：`SELECT table_metadata_id, MAX(access_time) ... GROUP BY table_metadata_id`
  —— **无时间下界、无索引**，每晚对全表做一次扫描 + 分组；
- `buildTopReaders`：`WHERE table_metadata_id=? AND access_type IN (...) AND access_time>=? GROUP BY user_name`。

埋点表只增不删 ⇒ 该扫描成本随埋点量线性上升。

### P1（设计冗余 / 语义不清）

**P1-1 同一份热度存了三处，且其中一处只写不读**
`table_metadata`（4 冗余列）、`asset_catalog_daily`（同 4 列）、`asset_usage_daily`（按日）。
其中 `asset_catalog_daily.browse_count_30d / read_count_30d / bookmark_count / last_access_time`
**全仓库只有写入方（`AssetCatalogSnapshotService.buildRow`），没有任何读取方** —— 纯死列。

**P1-2 `asset_usage_daily.relate_count` 是死列**
DDL 有、实体有，`rollupDaily` 里 `counts[3]` 从未自增，全仓库无读取方。

**P1-3 hot_score 算法相对化 + 不衰减**
`refreshColumnHotScore` 按"当天被命中的字段"升序切成 5 档（`1 + i*5/total`），最低档也是 1 星；
跨天不可比，且未被访问的字段保留旧值不衰减。若 P0-2 修好后真正启用，这个口径需要先定义清楚。

**P1-4 写路径全是逐条，无批量**
`recordAccess` 逐条 insert；`rollupDaily` 逐条 select + insert/update；回写热度逐表 UPDATE。
在 47 张表规模无事，几千张表时 nightly 成本可观。

**P1-5 批量语义缺陷：`last_access_time` 只回写批次里最后一张表**
`recordAccess` 里 `latestTableId` 在循环中被反复覆盖，只有批次**最后一个** table 项会被
`touchLastAccessTime` 实时回写。前端单条上报掩盖了这一点，但接口契约声明是批量。

**P1-6 埋点无节流/去重**
目录树来回点、预览反复 reload 都会重复计数；`read` 由 `useEffect` 依赖 `[status, reload]` 触发，
点"刷新"也会再计一次。热度可被无意刷高。

**P1-7 `touchLastAccessTime` 多一次无用读**
每次埋点先 `selectById` 再 `updateById`，返回值未使用，可直接 UPDATE。

## 三、表设计是否合理

### 结论

**骨架合理**：分层（明细 → 日汇总 → 冗余列）是标准做法，写多读少场景下正确；
**但存在 2 处死字段、1 处三重重冗余、缺保留期、缺一个关键索引。**

### 合理的部分

| 设计 | 评价 |
|---|---|
| 埋点独立于 `operation_audit_log` | 正确：避免浏览记录淹没操作留痕 |
| `asset_access_log` 仅追加 + `asset_usage_daily` 按日覆盖写 | 正确：T+1 幂等可重放 |
| `asset_usage_daily` 唯一键 `(asset_type, asset_id, stat_date)` | 正确：防重、支持覆盖 |
| `asset_bookmark` 唯一键 `(user_id, asset_type, asset_id)` | 正确：防重复收藏 |
| `asset_tag_rel` 多态 `(asset_type, asset_id)` + `table_metadata_id` 冗余 | 可用：便于按表聚合 |
| 4 方言 DDL 齐平（pg/h2 用独立 `CREATE INDEX`） | 好 |
| 冗余列换掉目录列表的 join | 思路对，但见 P1-1 |

### 不合理 / 待改

| 项 | 问题 | 建议 |
|---|---|---|
| `asset_catalog_daily` 4 个热度列 | 只写不读，与 `table_metadata` 重复 | 删除，或明确消费方 |
| `asset_usage_daily.relate_count` | 死列 | 删除 |
| `asset_access_log` / `asset_usage_daily` | 无保留期，与另两张 daily 表不一致 | 加 `RETENTION_DAYS` + `purgeBefore` |
| `asset_access_log` 索引 | 缺 `table_metadata_id`（含 `access_time` 复合）| 补 `idx_asset_access_table(table_metadata_id, access_time)` |
| 多态外键 `asset_type/asset_id` | 无约束，`table_metadata_id` 可能为空 | 可接受，但查询需容错（现状 `resolveTableIdOfColumn` 返回 null 已处理） |
| 热度三处存储 | 无单一事实源 | 明确 `asset_usage_daily` 为明细事实源、`table_metadata` 为读优化副本 |

## 四、建议的修复优先级

1. **定义清楚「访问频率」是什么**：若目标是"真实数据使用热度"，必须在数据探索 / 查询执行 /
   调度产出侧补 `read`/`query` 埋点，或接库侧统计（`pg_stat_*`）；否则应把 UI 文案改为"目录浏览热度"，避免误导。
2. **修 P0-2**：前端补 `column` 埋点（详情页字段行点击）或删除字段热度功能，二者择一。
3. **修 P0-3 / P0-4**：给 `asset_access_log` 加保留期清理 + `table_metadata_id` 索引。
4. **清 P1-1 / P1-2**：删死列，收敛冗余。
5. **P1-4 / P1-5 / P1-7**：批量 upsert、all-ids 回写 `last_access_time`、去掉多余 selectById。
6. **P1-6**：埋点侧加"同用户同表 N 秒去重"节流。
