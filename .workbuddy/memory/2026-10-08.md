# 2026-10-08 — 把 spark-listener(写入合规监听器)集成进 docker 的 Spark 环境

## 做了什么

把 `~/Desktop/spark-listener`（`com.writecompliance:spark-write-compliance`）集成到
`dataforge-docker` all-in-one 镜像里的 **Spark 3.5.9 (local)**，做到全局装载、无需改作业代码。

### spark-listener 侧改动

- 新增 **`spark-3.5` 适配模块**（Scala 2.12 / `spark-sql_2.12:3.5.9` provided），与容器 Spark 版本对齐；
  根 pom 注册该模块。2.4 / 3.1 / 3.5 / 4.1 四个适配模块源码保持完全一致。
- 四个适配模块统一新增 **`WriteComplianceSparkSessionExtension`**：public 无参构造、继承
  `scala.runtime.AbstractFunction1`（不能直接 implements `Function1`——Scala 2.11 的
  `apply$mcVJ$sp(long)` 等特化方法在接口里是抽象的，纯 Java 实现编译不过），供
  `spark.sql.extensions` 反射装载。
- `WriteComplianceQueryExecutionListener` 增加 **public 无参构造 + 懒加载配置**
  （全局 GLOBAL → 构造期注入 → `SparkSession.active()` → 兜底禁用），供
  `spark.sql.queryExecutionListeners` 反射装载。
- 新增回归测试 `spark-3.5/src/test/.../ConfigSupportTest.java`、`SparkReflectiveLoadingTest.java`
  （给 spark-3.5 模块加了 junit test 依赖）。

### 修掉的两个既有 bug（重要，属于"组件从 SparkConf 读配置一直不生效"的根因）

1. `ConfigSupport.fromSparkConf` 用 `instanceof Iterable` 判断 `SparkConf.getAll()` 的返回值，
   但它各版本都返回 **Java 数组 `scala.Tuple2<String,String>[]`** → 永远拿不到配置。
2. 同文件 `productParts` 用 `instanceof Iterable` 判断 `productIterator()` 的返回值，
   但它返回 Scala `Iterator`（2.11/2.12 是 `TraversableOnce`、2.13 是 `IterableOnce`），
   同样不是 `Iterable`。改为直接按 `scala.Tuple2._1()/_2()` 取值。

### 关键兼容性发现（Spark 3.5 起）

`org.apache.spark.deploy.SparkSubmitArguments` 会丢弃 spark-defaults.conf 与 `--conf` 中
**所有非 `spark.` 前缀**的配置项（只打 `Ignoring non-Spark config property` 告警）。
实测（Spark 3.5.9）：

| 下发方式 | 是否进 SparkConf |
| --- | --- |
| `--conf write.compliance.enabled=true` | ❌ |
| `--conf spark.write.compliance.enabled=true` | ✅ |
| spark-defaults.conf 里写 `write.compliance.*` | ❌ |

→ `ConfigSupport` 增加 `spark.write.compliance.*` 别名归一化（原名优先），
容器侧一律用 `spark.write.compliance.*`。

### docker 侧改动

- 新增 `build/conf/spark-defaults.conf`（把原先 Dockerfile 里的内联 printf 抽成仓库文件，
  增量构建也能刷新）。
- `build/build-lib.sh` 新增 `ensure_spark_listener()`：从 `SPARK_LISTENER_DIR`

- 新增 `build/scripts/set-write-compliance.sh`：容器内模式切换 `status|on|strict|off`，
  改写 spark-defaults.conf 中带标记的托管块。

## 验证结论（Spark 3.5.9 真机 + dataforge-allinone 容器）

- 分析期阻断：`CREATE VIEW/`CREATE TABLE ... AS SELECT` 命中规则 → 退出码 1，异常信息
  `[write-compliance] 检测到不合规写入：...命中禁止规则 ...`；不命中 → 退出码 0。
- 权限校验回调真实 dataforge-server（8082/api）：`user=admin` 放行；`user=test` 被拦；
  服务不可达 → fail-close 阻断。
- `spark.sql.extensions` / `queryExecutionListeners` 均被 Spark 成功反射装载
  （故意写错类名会报 `ClassNotFoundException` / `Cannot use ... to configure ...`）。
- 单元测试：core 17 个 + spark-3.5 6 个全绿。

## 环境坑

- **`docker build` 在本机被 buildx 卡住**：`failed to update builder last activity time: rename
  ~/.docker/buildx/activity/... operation not permitted`，与沙箱无关（`docker run` 正常）。
  **可行解法**：`cp -R ~/.docker/cli-plugins /tmp/dkcfg/`（连同 config.json、contexts），
  然后 `DOCKER_CONFIG=/tmp/dkcfg docker buildx build ...` —— 只搬 config 不搬 cli-plugins 的话
  `docker buildx` 会变成"unknown flag"（插件找不到）。已用该方式成功跑通 `./build/build.sh`。
- **zsh 不做无引号变量的词分割**：`$MOUNTS`、`$FLAGS` 这类多参数变量在 zsh 里会整体当做一个参数；
  验证脚本需用 `bash -c '...'` 包裹。build 脚本本身是 `#!/usr/bin/env bash`，不受影响。
- 后台任务（`run_in_background`）似乎不继承沙箱豁免，会被 file policy 拦（读 build/scripts/*.sh 被拒）；
  需要免沙箱的构建请前台执行。
- 容器内 `curl localhost` 需要 `--noproxy '*'`。

- 新镜像起真容器端到端复验通过：默认档 `user=admin` 放行；`strict` 档按 Spark 运行用户 → 服务端 400 → fail-close 阻断。
- **既有覆盖缺口（未修，已写入两处 README 已知限制）**：`INSERT OVERWRITE DIRECTORY '<path>'`
  在 analyzed 计划里是 `InsertIntoHiveDirCommand`（未启用 Hive 时为 `InsertIntoDir`），
  该节点名不在 `WriteTargetExtractor.V1_WRITE_NODES` 里，且目标在 `storage.locationUri`（`Option[String]`），
  `candidateString` 也不解包 `Option` → 这类"写目录"规则与权限校验都拿不到目标。
  注意 `InsertIntoHadoopFsRelationCommand`（`df.write.<format>(path)`）**在**名单里且工作正常，
  不要被表名误导。

## 补缺口：写目录（INSERT OVERWRITE DIRECTORY）已覆盖

改动集中在 core 的 `WriteTargetExtractor`（`DataResourceExtractor` 复用它的写入提取，所以一处修好两条路径都通）：

1. `V1_WRITE_NODES` 增加 `InsertIntoHiveDirCommand`、`InsertIntoDir`。
2. `readTargetString` 增加嵌套读取 `storage.locationUri`（并用 `Reflect.optionValue` 解包 Option）；
   同时 `candidateString` 开头统一解包 `Option`，避免出现 `Some(...)` 这种脏值。
3. `guessType(simpleName, target)` 现在会真正产出 `WriteTarget.Type.PATH`
   （字符串形态含 scheme / 以 `/` 开头，或节点属 `DIR_COMMAND_NAMES`），
   `RuleEngineTest` 早就在用 `Type.PATH`，但历史实现恒返回 TABLE。
4. `DataResourceExtractor.extractWrites` 改为按 `WriteTarget.Type` 分派 FILE/TABLE，不再用 `looksLikePath` 猜。
5. 测试：core 由 17 → 20 个（新增 `extractsDirWriteTargetFromStorageLocation`、
   `optionNoneLocationYieldsNoTarget`、`treatsDirWriteAsFileResource`）。

镜像已重建；真容器（新镜像）四条用例全绿：
规则命中 `/tmp/out/demo` → 阻断（此前放行）；不命中 → 放行；
权限路径目录写入上报 FILE 资源、`user=test` 被拦（此前放行）；CTAS 表名规则与 admin 放行无回归。

**踩坑提醒**：macOS BSD grep 不支持 BRE 的 `\|` 交替，`grep "a\|b"` 会静默无结果，用 rg/Grep 工具或 `grep -E`。
