## 清理容器内 DolphinScheduler 的全部补数任务

需求：把容器 `dataforge-allinone` 里 DS 的补数任务全部删除。

### 摸清的事实（重要，下次直接用）

- DS 是 **standalone 单进程**（`org.apache.dolphinscheduler.StandaloneServer`，supervisord 程序名 `dolphinscheduler`，
  脚本 `/opt/dataforge/scripts/run-ds-standalone.sh`），API 在 `127.0.0.1:12345`，context-path `/dolphinscheduler/`。
- **DS 的库不是 h2**：官方 `standalone-server/conf/application.yaml` 虽然默认 `spring.profiles.active: h2`，
  但启动脚本用环境变量把它改成了**容器内 PostgreSQL**：`jdbc:postgresql://127.0.0.1:5432/dolphinscheduler`，
  用户 `postgres` / 密码 `123456`，同时 `SPRING_PROFILES_ACTIVE=postgresql`（为了 Quartz 用 PostgreSQLDelegate）。
  直接用 `PGPASSWORD=123456 psql -h 127.0.0.1 -U postgres -d dolphinscheduler` 就能查。
- DS 版本 **3.4.1**，表名是新命名：`t_ds_workflow_instance` / `t_ds_workflow_definition`（不是 process_*）。
- **"补数"= `t_ds_workflow_instance.command_type = 5`（COMPLEMENT_DATA）**；`command_type=7` 是 REPEAT_RUNNING（重跑），
  两者在 DS UI 里是同一个实例列表，但语义不同，别一起删。
- 工作流实例的 REST 接口（前端 `src/api/dolphinscheduler.ts` 就在用）：
  - 列表 `GET /projects/{projectCode}/workflow-instances`
  - 停止/控制 `POST /projects/{projectCode}/executors/execute`，表单 `workflowInstanceId` + `executeType=STOP`
  - 删除 `DELETE /projects/{projectCode}/workflow-instances/{id}` —— **只允许删终态实例**，RUNNING 会报 code 50006
  - 认证：请求头 `token: <t_ds_access_token.token>`，库里已有 test_tenant 的长期 token（2029 到期），
    用 `psql -tA -c "select token from t_ds_access_token order by id limit 1"` 取即可。
  - 项目 code：`test_project = 183115978154240`。

### 踩到的坑

1. **DS 崩溃后会把 RUNNING 实例"自动恢复"重跑**。这次 DS 因内存打满（容器 8G，master `-Xms4g -Xmx4g`
   + 4 个 Spark local 作业 + marquez + dataforge-server 同时跑）用 `ExitOnOutOfMemoryError` 退出，
   supervisord 拉起新进程后，master 又把这 4 个 `RUNNING_EXECUTION` 的补数实例重新调度起来，
   导致"停不掉 / 删不掉 / 内存再次打满"的死循环。
2. 刚重启完的瞬间调 STOP 会失败：`Cannot find the WorkflowExecuteRunnable: {id}`（恢复还没跑完）。
3. 容器内 curl 必须加 `--noproxy '*'`。

### 最终做法（可复用）

```bash
# 1) 先停 DS，断掉自动恢复
supervisorctl stop dolphinscheduler
# 2) 杀掉残留执行体，释放内存
pkill -9 -f "dolphinscheduler/exec/process"; pkill -9 -f "sudo -u test_tenant"
# 3) 直接清库（先子后父，外键相关表见 information_schema）
#    t_ds_task_instance_context -> t_ds_task_instance -> t_ds_task_group_queue
#    -> t_ds_relation_workflow_instance -> t_ds_command/error_command
#    -> t_ds_serial_command -> t_ds_alert -> t_ds_workflow_instance
# 4) 再尾部清理孤儿行：serial_command / command / relation_workflow_instance 里
#    workflow_instance_id 已不存在的记录（串行补数队列的残留）
supervisorctl start dolphinscheduler
```

结果：删除 4 个工作流实例 + 305 个任务实例 + 57 条 task_instance_context + 3 条 serial_command 残留；
`t_ds_workflow_instance` 只剩 1 条 `command_type=7`（ode 重跑，已 SUCCESS，非补数，保留）。
DS 重启后 `/actuator/health` 全 UP，容器 CPU 从 438% 降到 8%。

删除前做了全库快照：容器内 `/tmp/ds_backup_before_clear.sql`（2.9MB，pg_dump 纯文本，可 psql 直接恢复）。

## "kill DS 进程后不断自动启动"的机制排查（22:10）

现象：直接 kill 容器里 DS 的 java 进程（`org.apache.dolphinscheduler.StandaloneServer`）后秒级被拉起，反复出现。

**机制（三层）**：
1. 容器 PID 1 = supervisord（`CMD=/usr/bin/supervisord -c /etc/supervisor/supervisord.conf`）。
   `build/conf/supervisord.conf` 的 `[program:dolphinscheduler]` 是 **`autorestart=true` + `startsecs=15`**
   → 进程一退出就无条件重启。
2. **真正被托管的进程不是 java，而是包装脚本**：`command=/opt/dataforge/scripts/run-ds-standalone.sh`。
   脚本第 43/44 行先 `dolphinscheduler-daemon.sh stop` 再 `start`（nohup 异步起 java），
   末尾 `while pgrep -f StandaloneServer; do sleep 15; done; exit 1`。
   → java 一消失，**脚本自己 exit 1**，supervisor 认为程序挂了 → 重启脚本 → 脚本又 stop+start。
   **这就是"kill java 无效"的直接原因。**
3. `HostConfig.RestartPolicy=unless-stopped` 只管容器级，本次不是主因。

→ **正确停法：`docker exec dataforge-allinone supervisorctl stop dolphinscheduler`**（记忆里已有，本次再次验证）。
   补充：`[program:dolphinscheduler]` 段**缺 `stopasgroup/killasgroup`**（postgres 段有），
   stop 之后 java 可能变孤儿继续占 12345，需补一刀 `pkill -f org.apache.dolphinscheduler.StandaloneServer`。

**顺带查到的真实隐患（比"停不掉"更该修）**：
- supervisor 日志统计：**今天 DS 被重启 55 次**（13:04~14:11 这一小时内就 17 次），每次都是 `exit status 1; not expected`。
  DS 自身日志该小时有 **1116 条 Shutdown / 279 条 stopping / 17 次 Started StandaloneServer**。
- 容器 cgroup：`memory.max = 8GiB`，**`/sys/fs/cgroup/memory.events` 的 `oom_kill = 74`**（累计被内核 OOM killer 杀 74 次）。
- **关键判据**：DS 反复退出却**既没有 `hs_err_pid*.log` 也没有 `dump.hprof`** → 不是 JVM 堆内 OOM
  （那会触发 `-XX:+ExitOnOutOfMemoryError` / `+HeapDumpOnOutOfMemoryError` 留证），而是**被 SIGKILL 直接干掉**，
  符合 cgroup OOM killer 的行为。所以"不断自启"= **内存超限被杀 + supervisord 秒级拉起** 叠加成的死循环。
  （注：07 点前那条日志把原因写成 "ExitOnOutOfMemoryError 退出"，本次证据表明更可能是 cgroup OOM kill，以本次为准。）
- 修复方向：① `bin/env/dolphinscheduler_env.sh` 里 DS 的 `-Xms4g -Xmx4g` 降到 1~1.5g（8G 容器里 4G 堆太贪）；
  ② supervisord 给 dolphinscheduler 补 `stopasgroup=true`/`killasgroup=true`；③ Spark local 作业不要与 DS 并发跑；
  ④ 容器 8G 是 allinone 的既定约束，不宜再加组件。
- 小 bug：JAVA_OPTS 里 `-Duser.timezone=${SPRING_JACKSON_TIME_ZONE}` 变量没展开，字面量传给了 JVM。

### 本轮修复（22:00-22:30，只做存储/元数据侧；调度相关用户要求暂缓）

改动 10 个文件（+336/-47），新增 1 个类 + 5 个单测用例：
- **`JdbcTableStatsCollector.POSTGRES_STATS_SQL`**：分区父表大小/行数改为 `自身 + sum(分区子表)`，
  并 `AND NOT c.relispartition` 排除子表。这是"体积少算 3.7 倍"的根因。
  PG 的 `pg_total_relation_size(父)` 恒为 0，而子表又被 `removePostgresPartitionChildren()` 剔出元数据。
- **`ExecutionStrategy.listTableRowCounts`**（新默认方法）+ `AbstractJdbcExecutionStrategy` 实现；
  行数取 `reltuples`，**负数(-1)按未知处理返回 null，0 是合法值要写**。
  注意 `n_live_tup` 在本机不能用来兜底（29 行的表报 4）。
- **`TableStorageSizeRefreshService`**：一轮里同时覆盖写 `size_bytes` + `row_count`（原来只写 size）。
- **`AssetDailyTaskCatchUpRunner`**（新）：`ApplicationReadyEvent` 时若 `asset_catalog_daily`/`asset_usage_daily`
  从未产出过则补跑昨天。**带新鲜度守卫**：`max(sync_time) < 统计日` 时跳过，避免把过期元数据固化成历史基线
  （大小增长率要拿它当基线，错了会一直错）。
- **伪业务域**：`TableNameConventionParser` 是刻意设计（`TableNameConventionParserTest#unknownLayerStillExtractsDomain`
  有测试背书），**不能改解析器**；改的是盘点聚合侧——`AssetInventoryService` 两处 byDomain 都加
  `layerCode != null` 守卫。同理 `AssetEnvParser` 加了 `ENV_UNKNOWN`，`envProject`/`topAssets`/`sizeGrowth`
  不再 `continue` 丢弃识别不出环境的库。

byDomain 8 个伪域→只剩 olist；env-project 1 行→2 行（多出 unknown 179MB）；
`table/65` 的 rowCount/sizeBytes 从 null 变成 1000163/135159808。
单测：相关 26 例 + asset 包 67 例全绿。

**部署方式**：`mvn -o -q -DskipTests package` → `docker cp` 到 `/opt/dataforge/dataforge-server.jar`
