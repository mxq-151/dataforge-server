## 排查：远程环境报 `column "business_owner" does not exist` (Position: 325)

**这是"无 schema 迁移机制"的必然结果，不是镜像构建问题。** 远程环境的 `dataforge` 库是老的，
新镜像里新增的列永远不会补上去。定位链条（全部可复核）：

1. `TableMetadata` 实体（`modules/metadata/entity/TableMetadata.java` 第 47-58 行）有 6 个
   「资产目录治理属性」字段：`businessOwner/techOwner/topic/visibility/categoryCode/assetLevel`，
   共 31 个字段；MyBatis-Plus 的 `getOne` 会把**全部 31 列**写进 SELECT。
2. 这 6 列在 `table_metadata` 上是 **commit `9812bbe`（2026-09-23「增加数据质量和资产目录功能」）**
   一起加的：此前 `table_metadata` 是 26 列（25 列 + 旧 `deleted`），此后 31 列。
3. **`Position: 325` 就是 `business_owner` 在 MP 生成 SELECT 里的下标**（实体字段序，
   `SELECT ` 前缀后第 324 字符，MP 前置 1 个空白 → 325）。即目标库的 `table_metadata`
   恰好停在"前 25 列都有、第一个治理列就缺"的老形态。
4. 同名现象**只报第一列**：PG 解析到第一个无法解析的标识符就停，所以 `tech_owner/topic/...`
   是否也缺不会出现在同一条错误里（实际几乎必然一起缺）。
5. `UnexpectedRollbackException` 是次生现象，不是独立故障：
   `MetadataSyncService.syncAllMetadataByDatasourceId`（第 143-163 行）对每张表
   `try { ... syncSingleTable } catch (Exception e) { log.error; failCount++ }` —— **异常被吞掉**，
   但 `syncSingleTable` 是 `@Transactional` 且加入同一事务，抛异常时事务已被标记 rollback-only，
   于是方法正常返回、提交时抛 `UnexpectedRollbackException`。

**根因：项目已无迁移能力。** `src/main/resources/sql/` 下只有 `init/` + `testdata/`
（`migrate/` 2026-10-09 已删）；`init-dataforge.sh` 第 63 行的守卫是
`if ! SELECT 1 FROM information_schema.tables WHERE table_name='sys_user'` ——
**全有或全无**：只要库里已有 `sys_user` 就整段跳过 schema 导入；应用侧也完全没有建表/改表逻辑
（`src/main/java` 无 `CREATE TABLE`/SchemaInitializer）。所以任何新增列只对**全新库**生效。

**给远程库补列（PG）**：
```sql
ALTER TABLE table_metadata
  ADD COLUMN IF NOT EXISTS business_owner VARCHAR(255),
  ADD COLUMN IF NOT EXISTS tech_owner     VARCHAR(255),
  ADD COLUMN IF NOT EXISTS topic          VARCHAR(200),
  ADD COLUMN IF NOT EXISTS visibility     VARCHAR(20) NOT NULL DEFAULT 'internal',
  ADD COLUMN IF NOT EXISTS category_code  VARCHAR(64),
  ADD COLUMN IF NOT EXISTS asset_level    VARCHAR(16);
CREATE INDEX IF NOT EXISTS idx_table_metadata_owner ON table_metadata (business_owner);
```
注意：若远程库真是 2026-09-23 前建的，还会**整体缺 11 张表**（`asset_catalog_daily`
`asset_category` `asset_doc` `asset_doc_history` `asset_tag` `asset_tag_rel` `dq_rule`
`dq_rule_result` `dq_rule_template` `scheduler_task_run_daily` `table_partition_size_daily`），
补完列还得把当前 `init/dataforge-postgresql.sql` 整跑一遍（`CREATE TABLE IF NOT EXISTS` 幂等，只补表不补列）。
**所以先做列级 diff 再动手**，别只盯 `business_owner`。

## 根治：init 脚本自带「既有库自愈」（不用迁移机制）

按"不要迁移数据库、直接改 init 脚本"的要求落地，改动 3 类文件：

1. **新增 `build/gen_init_schema_sync.py`**：从 4 份 `sql/init/dataforge-*.sql` **自身的建表段**
   解析出全部列/约束（38 表 / 472 列 / PG 25、MySQL 88、H2 2 条约束），生成幂等补齐 SQL，
   插在 `BEGIN/END AUTO-GENERATED SCHEMA SYNC` 标记之间。`--check` 模式供 CI。
2. **4 份 init SQL**：新增"既有库补齐段"+ 种子 INSERT 幂等化。
   - PG：`DO $$` 块，`information_schema`/`pg_constraint` 存在性判断 + 动态 ALTER，
     每条 ALTER 各自 `EXCEPTION WHEN OTHERS` 降级为 WARNING。
   - MySQL/MariaDB：存储过程 `df_sync_add_column` / `df_sync_add_index` + `CALL` 列表（含 DELIMITER）。
   - H2：`ALTER TABLE **IF EXISTS** t ADD COLUMN IF NOT EXISTS ...`。
   - 种子 INSERT：PG `ON CONFLICT DO NOTHING`、MySQL/MariaDB `INSERT IGNORE`、
     H2 `INSERT ... SELECT ... WHERE NOT EXISTS`（H2 没有前两者）。
3. **`build/scripts/init-dataforge.sh` 第 4 步**：删掉「`sys_user` 存在就跳过 schema 导入」的守卫，
   每次启动都全量执行，并把 `ERROR:` 计数打出来（原来是 `>/dev/null 2>&1` 静默吞错）。

**踩过的三个坑（写进脚本注释了，别改回去）**：
- 补齐段最初生成在**文件末尾** → 老库上第 227 行 `COMMENT ON COLUMN column_metadata.business_desc`
  先因缺列报错，PG 里 **abort 整个事务**，后面 144 条全是 "current transaction is aborted"，
  补齐段永远执行不到（老库跑完还是 27 表）。→ **必须放建表段之前**。
- 即便前置，若留在 `BEGIN;` 之内，后面任一错误回滚会把补好的列一起撤销 → **PG 必须放在 `BEGIN;` 之前**。
- 生成器自身不幂等：补齐段前移后，原 `parse()` 用 `text[:find(BEGIN_MARK)]` 截断会把 DDL 也切掉，
  第二次运行会生成空段 → 改成 `remove_block()` 摘标记区间。
- H2：`ALTER TABLE` 不带 `IF EXISTS` 时表不存在会报 `Table not found` 并中断脚本。

**验证（4 方言各 4 个场景，全部通过）**：
| 场景 | PG | MySQL | MariaDB | H2 |
|---|---|---|---|---|
| 老库(2026-09-23 前) 建立 | 27 表 / 无 business_owner | 同 | 同 | 同 |
| 全新库跑新脚本 | 0 错 / 38 表 | 0 错 / 38 表 | 同 | 0 错 / 38 表 |
| **老库跑新脚本(自愈)** | **0 错 0 警 / 38 表 / business_owner 已补** | 同 + 索引唯一键齐全 | 同 | 同 |
| 幂等重跑 ×2 | 0 错 | 0 错 | 0 错 | 0 错 |
| 种子行数(应 1/1/7/7/4) | 1/1/7/7/4 | 1/1/7/7/4 | 1/1/7/7/4 | 1/1/7/7/4 |

逐列断言：自愈后老库覆盖脚本声明的全部 38 表 / 472 列 / 25 约束，只多出 13 个历史遗留 `deleted` 列。
验证用的临时库（容器 `df_v_*`、MySQL `df_v_*`、H2 文件库）与临时文件均已清理。

**遗留提醒：修复要生效，`df-data` 命名卷必须先刷新**——它遮蔽了镜像里的 `/opt/dataforge/sql/`，

## 追加：`InvalidDefaultArgInFrom` 警告 + 远程镜像实际校验

用户跑 `REGISTRY=crpi-.../dataforge_docker/ ./build/build-all.sh` 看到
`1 warning found - InvalidDefaultArgInFrom: Default value for ARG ${BASE_IMAGE} ... (line 2)`，
以为是报错。**实际是 BuildKit 的 Dockerfile lint 警告，不影响构建**——staging Dockerfile 里
`ARG BASE_IMAGE` 没有默认值，而 `--build-arg BASE_IMAGE=...` 每次都会传，所以构建正常。
已于 `build-lib.sh` 改成 `ARG BASE_IMAGE=dataforge-allinone:1.0`（默认值不会被用到，只为过 lint）；
实测重跑 `./build.sh`：退出码 0、warning 计数 0。`build/Dockerfile` 的 FROM 都是字面镜像，无同类问题。

**顺带验证了用户的推送结果（用 `docker buildx imagetools inspect`，只读、不用拉 7GB）**：
- 仓库 tag 已是双架构 OCI index（linux/amd64 `9b1c41c9…`、linux/arm64 `7e5a28a7e1f6…`）；
- 两个架构 config 的 `Entrypoint`/`Cmd` 都已是新值；
- **linux/arm64 的 manifest 摘要 = 我本地已验证镜像的摘要（`7e5a28a7…`）** —— 说明用户那次
  `build-all.sh` 推上去的就是修复后的镜像（多架构 arm64 与本地单架构构建内容一致，因为
  两次的 base 都是仓库里的 `cb9eb786`、staged 文件也相同）。
- 结论：**该 tag 可直接部署，无需重新 push**；重跑只是为了拿到干净日志。
- 可用命令：`docker buildx imagetools inspect <tag>` 看是否双架构；
  `docker buildx imagetools inspect <tag>@<digest> --format '{{json .Image.Config}}'` 看 Entrypoint/Cmd。
