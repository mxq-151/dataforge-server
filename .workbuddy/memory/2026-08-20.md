## 大数据组件版本耦合分析
分析 bigdata-platform 项目对大数据组件的版本绑定情况（结果见与用户的对话）。

结论要点：
- **编译期硬绑定版本**：hadoop-client 3.4.3(HDFS)、juicefs-hadoop 1.3.1、kyuubi-hive-jdbc 1.11.1、hbase-client 2.5.9、calcite-core 1.37.0、orc-core 1.9.2(nohive)、parquet-avro 1.13.1、jsqlparser 4.9、aws-sdk-s3 2.21.1。
- **构建期完全解耦**：Spark（外部 spark-submit/spark-sql，home 路径 spark-4.1.1-bin-hadoop3）、Flink（外部 flink 命令 /opt/flink）；Doris/ClickHouse 经 MySQL JDBC 驱动（com.mysql.cj.jdbc.Driver）接入，无专属客户端；Hive 经 Kyuubi JDBC，集群版本决定。
- **风险点**：Iceberg/Hudi 在 StorageEngineType 枚举但无客户端依赖；ClickHouse 走 MySQL 协议缺失原生特性；JuiceFS 1.3.1 未对 hadoop 依赖做 exclusion，需确认与 3.4.3 兼容。
- pom 对 kyuubi/hbase 大量 exclusion 把 hadoop 版本收敛到 3.4.3，正确但运行时版本由它定调。

## 修复：审计日志分区存储过程缺失
- **症状**：`AuditLogPartitionTask`（每天 02:00 / 每月 1 号 03:00）报 `PROCEDURE dataforge.sp_create_audit_log_partition does not exist`。
- **根因**：`dataforge.sql` 是 mysqldump 表结构备份，默认不导出存储过程（需 `--routines`），两个过程从未创建。
- **修复**：新增 `src/main/resources/sql/dataforge_partition_procedures.sql`，创建 `sp_create_audit_log_partition`（REORGANIZE p_max 拆分未来 30 天日分区，因 MAXVALUE 必须是末分区不能直接 ADD）与 `sp_cleanup_audit_log_partitions`（按 pYYYYMMDD 命名清理 90 天前分区，保留 p_max）。已在本机 MySQL 9.6 执行并验证：30 个日分区 + p_max = 31 个，幂等、清理均正常。
- **注意**：后续重新导入 dataforge.sql 会再次丢失存储过程，备份需加 `--routines` 或将本脚本一并执行。

## 变更：分区维护改 Java 实现（弃用存储过程）
用户要求不用存储过程。已将 `AuditLogPartitionTask` 重写为纯 Java + JDBC：
- 每日 02:00 `createNextPartition()`：查 information_schema.PARTITIONS 判断缺失，用 `REORGANIZE PARTITION p_max INTO (pYYYYMMDD VALUES LESS THAN (TO_DAYS(...)), p_max)` 拆分，保障未来 30 天日分区。
- 每月 1 号 03:00 `cleanupExpiredPartitions()`：按 `PARTITION_NAME REGEXP '^p[0-9]{8}$'` 且 `< p{cutoff}` 清理 90 天前分区，永不删 p_max。
- 已删除 `dataforge_partition_procedures.sql` 脚本并 DROP 库中两个存储过程；`mvn compile` 通过；REORGANIZE DDL 实测成功（建 p20260919 后移除恢复 31 分区）。
- **经验**：MAXVALUE 分区是末分区，创建日分区必须 REORGANIZE p_max 拆分，不能直接 ADD PARTITION；information_schema.PARTITIONS 查询需注意 JDBC 连接默认库=DATABASE()。

## MySQL 5.7 适配优化（AuditLogPartitionTask）
- **关键差异**：5.7 中 REORGANIZE/DROP PARTITION 是 COPY 算法（全表重建+锁表），8.0 起才是 INPLACE（仅元数据）。逐分区循环在 5.7 会触发 N 次全表重建。
- **已优化**：改为一次 ALTER 批量处理——`existingPartitionNames()` 一次查询全部分区名(Set)，缺失分区合并为一次 `REORGANIZE p_max INTO (多分区定义, p_max)`，过期分区合并为一次 `DROP PARTITION p1, p2, ...`（5.7/8.0/9.6 均支持多分区语法，已实测）。mvn compile 通过。
- 5.7 其他注意：单表分区上限 1024（8.0 为 8192），当前 ~120 无压力；5.7 分区表唯一键必须含分区键（建表约束）；information_schema.PARTITIONS 在 5.7 查询较慢但低频可接受。
